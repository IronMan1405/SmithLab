# Architecture

SmithLab is a client-side single-page application: React 19, TypeScript in
strict mode, Vite and SVG rendering. There is no server. All mathematics runs
in the browser, and the expression text a user types is the only stored copy
of an expression.

## Dependencies between layers

The pure layers form a strict chain, and none of them uses React or the DOM:

```
core ← geometry ← expressions ← workspace
```

The UI layers sit on top. `chart` and `interaction` share a few things in
both directions: `interaction` uses the pure viewport mathematics in
`chart/viewport.ts`, and `chart` uses the hit-test attribute names and the
gesture type exported by `interaction`. `components` and `App.tsx` depend on
everything below them.

`core`, `geometry`, `expressions`, `workspace`, `chart/viewport.ts`,
`chart/svg-path.ts` and the `interaction` state machines are plain TypeScript.
They can be tested in Node and reused outside the browser, for example in a
worker or a command-line tool.

## Layer responsibilities

| Layer | Knows about | Does not know about |
|-------|-------------|---------------------|
| `core` | complex numbers, z, y, Γ, VSWR, lossless lines | geometry, SVG, React |
| `geometry` | circles, arcs and curves in the Γ-plane, grid layout, label anchors, coordinate modes | SVG pixels, React, CSS |
| `expressions` | syntax, types, functions, dependencies | rendering, the screen |
| `workspace` | points, derived points, guides, selection, Z₀, derived quantities | screen, SVG, React |
| `interaction` | pointer and keyboard semantics, thresholds | Smith Chart formulas, rendering |
| `chart` | SVG user space, the screen, React | Smith Chart formulas |

Each grid curve is built twice over. Its circle **centre and radius** come
from the closed-form equations in `geometry/*-circles.ts`, and its arc
**endpoints** come from mapping impedances through
`core.reflectionFromImpedance`. The tests check that the two agree.

## Interaction data flow

```
pointer / wheel / key event
  → useChartInteraction / useKeyboardShortcuts   (gather rect, hit target, modifiers)
  → gestures.ts / keyboard.ts                    (pure: decide, return commands)
  → App.applyCommand                             (the one place commands become state)
  → workspaceReducer / setView
  → SmithChart (render) + inspectors (quantities from core)
```

## Expressions as the source of truth

- Expressions are stored in workspace state as text records
  (`expressions/definitions.ts`). Everything else about them (parsed AST,
  values, curves, plot positions) is derived.
- `expressions/engine.ts` binds names, builds the dependency graph, detects
  cycles and evaluates in topological order. Evaluation is incremental: an
  expression is re-evaluated only when its text, enabled state, a name
  binding, a dependency's result, or (for expressions that use Z₀) Z₀ changes.
- Sliders and point drags rewrite the number in the expression text, so the
  text is always the only copy of a value.
- UI actions that create expressions (for example **+ Add transmission line**
  on an expression point) generate ordinary expression text through
  `expressions/constructions.ts`, so their mathematics lives in one place.

## Curves

`geometry/curves.ts` defines a `Curve` as:

- `point(t) → Γ`, the mathematical definition, over a finite named parameter
  interval;
- the exact `Shape` (circle, arc or segment) whenever one is known, or exact
  `pieces` for a curve made of several disjoint exact arcs;
- a `frame` (`number` or `plane`, see [Mathematics](mathematics.md#chart-coordinate-modes))
  and, for number curves, a domain (impedance or admittance);
- its defining properties, for display.

Curves with exact geometry render as true SVG arcs and are intersected
analytically. Generic parametric curves are sampled adaptively
(`curve-sampling.ts`) and intersected numerically. Sampled coordinates are a
cache, never stored state.

## Derived points

The manually placed points and their transmission lines use a small derived
point model, separate from expressions:

- A derived point stores `{ id, name, sourceId, transform: { type: 'line', length } }`
  and never a Γ. Its Γ is recomputed from the source by `resolveGamma`
  whenever it is needed, so it cannot go stale.
- `sourceId` may name another derived point, which is how chains are
  expressed: one transform per link, with no general graph framework.
- `PointTransform` is a tagged union, so new transforms add a case rather than
  changing the model.
- Dragging a derived point uses the same `point/move` command as any other
  point. For a derived point, the reducer changes its transform parameter
  instead of storing a position.

## The expression reference

The in-app reference is generated from the live registries in
`src/expressions/reference.ts`. Function names, signatures and descriptions
come from `FUNCTIONS` and `CURVE_FUNCTIONS`, constants from `CONSTANTS`, and
type names from `TYPE_INFO`. That module only adds categories, return types
and examples. `tests/reference.test.ts` fails if:

- a registry function is undocumented, or a documented one does not exist;
- any example does not evaluate to its documented type;
- an operator-rule or naming example misbehaves;
- an example set produces an error.

## Theming

All colours and line weights are CSS custom properties in
`src/styles/themes.css`, scoped by `[data-theme='light' | 'dark']` on
`<html>`. Components only use these variables. To add a theme, add another
`[data-theme='…']` block that defines the same tokens.

The theme preference (Light, Dark or System) is stored in `localStorage`. A
small inline script in `index.html` applies it before first paint, to avoid a
flash of the wrong theme.
